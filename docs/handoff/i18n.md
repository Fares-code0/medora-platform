# i18n and RTL — the architecture, and how to translate the rest

**Status:** the system ships and five locales are live (FRONTEND_CHECKLIST
F-19). The **shell** is fully translated; the **feature interiors** are not,
and this document is how the next person finishes them.
**Audience:** anyone adding a string, a screen, or a language.

---

## 1. What exists

`src/i18n/` — a platform layer. It imports nothing from `features/`, so any
feature may use it.

| File | Role |
| --- | --- |
| `locales.ts` | The `Locale` **union** (`en \| ar \| tr \| fa \| fr`), metadata, direction. |
| `messages/en.ts` | The source catalogue. English is the only file written as prose. |
| `messages/{ar,fa,tr,fr}.ts` | Translations, each typed `Messages`. |
| `messages/index.ts` | `catalogues: Record<Locale, Messages>` — total in both directions. |
| `LocaleProvider.tsx` | Sets `<html lang>` and `<html dir>`; persists the choice. |
| `locale-context.ts` | `useLocale`, `useDirection`, `useIsRtl`. |
| `useT.ts` | `t(key, params?)` with `{name}` interpolation. |
| `LocaleSwitcher.tsx` | The one language control, shared by login and Settings. |

The whole surface a feature touches is four things:

```tsx
const t = useT();            // t('nav.patients'), t('flow.stepOf', { step, total })
const { locale, setLocale } = useLocale();
const rtl = useIsRtl();      // only for what logical CSS cannot do
<LocaleSwitcher />
```

## 2. The two decisions everything else follows from

**Direction is a document property, set once on `<html>`.** Not a prop, not a
context read in each component, and emphatically not an RTL variant of any
component. `dir` inherits, so a component written in logical CSS mirrors
without knowing it exists. This is what makes RTL an attribute rather than a
rewrite — and why "do not duplicate components for RTL" was cheap to honour.

**Catalogues are total, and typed.** `Record<Locale, Record<MessageKey, string>>`
means a key added to `en.ts` without its four translations does not compile.
There is no "untranslated" runtime state to discover in the browser, and no
fallback chain to reason about. The predecessor was
`Partial<Record<string, …>>`, which is how a language ships half-translated
without anyone noticing.

## 3. Adding a string

1. Add the key to `src/i18n/messages/en.ts`, namespaced by surface.
2. Run `npm --prefix frontend run typecheck`. It names the four catalogues
   that are now incomplete.
3. Translate in each. Then `t('your.key')` at the call site.

**Interpolate; never concatenate.** `t('flow.stepOf', { step, total })`, not
`` `Step ${step} of ${total}` `` and not `t('flow.step') + n + t('flow.of')`.
Turkish suffixes depend on the preceding vowel and Arabic word order differs,
so a sentence assembled from fragments cannot be made correct in both.

## 4. Adding a language

1. Add the code to `LOCALE_CODES` and metadata to `LOCALES` in `locales.ts`,
   with the correct `dir`.
2. Add `messages/<code>.ts` typed as `Messages`.
3. That is all. The switcher, `<html lang>`, `dir`, persistence and the tests
   are all driven off `LOCALE_CODES`.

The typechecker lists every string still missing — you never have to click
through the app to find them.

## 5. Layout rules

**Write logical, always.** `ms-`/`me-`, `ps-`/`pe-`, `start-`/`end-`,
`text-start`/`text-end`, `border-s`/`border-e`, `rounded-s`/`rounded-e`.
`src/i18n/logical-properties.test.ts` scans all of `src/` and fails on a
physical one, because a stray `ml-4` looks correct in English and quietly
breaks a corner of two languages nobody on the team reads.

**The sanctioned exceptions**, allowed through that scan when written as an
explicit `rtl:` / `ltr:` variant:

- `transform` is physical in both directions — the `Switch` knob, a centring
  `-translate-x-1/2` under a `start-1/2`, a drawer's entrance offset.
- Gradient direction (`bg-gradient-to-r` → `rtl:bg-gradient-to-l`).

**Directional icons mirror through one CSS rule**, in `globals.css`: lucide
stamps each icon with its own class, so `[dir='rtl'] .lucide-chevron-right`
covers all 56 call sites. Add a new icon there only if its meaning is
*reading order*. `arrow-up-right` is deliberately excluded — it means
"trending up", a chart convention that reads the same in every script, and
mirroring it would turn growth into decline.

**Pin `dir="ltr"` on Latin-only runs.** An email, a version string, an MRN, a
code. Inside an RTL paragraph the Unicode bidi algorithm moves the trailing
run to the front: `© 2026 Medora · v0.1.0` renders as
`Medora · v0.1.0 2026 ©`. Isolate the run; do not reword it.

Clinical values are Latin-only runs too, and the ones that start or end
with a digit or a sign are the ones that move: a blood group (`O+` → "+O"),
a phone number (`+20 100 214 3387` → "3387 214 100 20+"), a dose or a
duration (`250 mg` → "mg 250"), a vital sign (`68 bpm` → "bpm 68"). Pin
each with an inline `<span dir="ltr">`, never on the `<dd>` or cell itself,
which would also flip its alignment. Two refinements (NEW-32):

- **Pin the whole Latin-only line, not the value inside it.** An isolate is
  a neutral to the paragraph around it, so `Blood <span dir="ltr">O+</span>`
  at the end of an English line carries `O+` to the far end of an RTL line.
  Wrap the sentence (`MRN … · 52 y · Male · Blood O+`) as one run instead.
- **A value after a Latin word is already in order.** `Glucophage 850 mg`
  reads correctly, because the drug name sets the run's direction. Pinning
  the dose alone detaches it — "850 mg Glucophage".

**When the value is a string prop**, the span cannot be placed: a status
badge's label, a select option, a radio description. Use `isolateLtr()` from
`@/i18n` (`src/i18n/bidi.ts`), which wraps the text in U+2066 … U+2069, the
plain-text form of the same isolate. `Select` matches typeahead through
`withoutIsolates()`, so an isolated option is still found by its first
character. Prefer the span wherever JSX allows it.

**Lab values are the case that matters most.** A value and its unit, and a
reference range and its unit, are each one run. Unpinned, `0.5 10³/µL` reads
"µL/0.510³" and `12.0–17.0 g/dL` reads "17.0g/dL –12.0", a range printed
backwards (NEW-32, pass 8).

**What is not a defect:**
- A percentage (`12.4%`): the sign binds to the number.
- A heatmap hour (`8a`).
- Two separate numbers laid out right to left (`143 · 15%`), which an RTL
  reader takes in the right order.

## 6. What is left, precisely

**~2,045 user-facing literals in feature interiors are still English**, by
area:

| Area | ≈ literals |
| --- | --- |
| `features/admin/sections` | 354 |
| `features/doctor/settings` | 178 |
| `features/doctor/pharmacy` | 163 |
| `features/doctor/medical-records` | 161 |
| `features/doctor/labs` | 158 |
| `features/doctor/patients` | 156 |
| `features/admin/doctors` | 104 |
| everything else | ~770 |

They are not blocked on anything — the mechanism is in place and the pattern
is one line per string. They are deliberately **not machine-translated**:
this is clinical software, and a plausible-looking wrong rendering of
"contraindication", "as needed", or "review before signing" is more dangerous
than a screen that is visibly still in English. Each area needs a translator
who reads clinical vocabulary in that language.

**The visible consequence, while they remain English**, is bidi reordering
inside the RTL locales: an English string ending in a number renders as
"appointments 5" rather than "5 appointments", because the RTL paragraph
direction moves the trailing Latin run. It is not a layout bug and it does
not have a layout fix — the fix is the translation. Do not paper over it with
a blanket `dir="auto"`: that would also flip genuinely Arabic text that
happens to begin with a Latin patient name.

## 7. Also not done

- **Dates and numbers — done (DEC-009, 2026-10-22).** Every date and number
  is formatted by `src/i18n/format.ts` (`formatDate`, `formatTime`,
  `formatDateTime`, `formatDateWith`, `formatNumber`) in the app's language:
  month and weekday names and date order follow it, **digits are Latin in all
  five languages** (an owner decision for clinical safety — one digit system
  for doses, lab values, IDs and dates). Never call `toLocaleString` or
  `new Intl.…Format` elsewhere: `format.test.ts` fails the build if you do.
  The **calendar is Gregorian in every language** (DEC-010, closed — no Hijri
  or Solar Hijri conversion; `format.ts` pins it). **Separators** are a dot
  decimal and a U+202F thin-space thousands separator in every language —
  `1 234.5` (DEC-011). Raw clinical values, number inputs and the server use a
  dot and no grouping, and are not touched by the formatter.
- **No pluralisation rules.** English "1 patient / 2 patients" is handled at
  call sites by hand. Arabic has six plural forms and Persian one; a real
  plural needs `Intl.PluralRules` and per-form catalogue entries.
- **The catalogues are not extracted to a translator-facing format** (no
  `.po`, no TMS). They are TypeScript objects, which the typechecker can
  verify and a translator cannot open. Worth revisiting at the point a real
  translator is engaged.
